# Phase 39 - Cron Jobs, the Boring Way (Which Is the Right Way)

Third of the four v1.0 items. Cron Jobs has been a dead entry in the account sidebar since it was
first added — a `Soon` badge and nothing behind it. Today it became real, and the interesting part
of building it was resisting the temptation to build something clever.

**A hosting panel's cron feature is a solved problem**: the OS already has one, and it already does
exactly what's needed — runs a command on a schedule, as a specific user, with output mailed
somewhere. The wrong way to build this is a Laravel-scheduled job that iterates a database table
every minute and shells out on everyone's behalf as root. That's a shared, single point of failure,
and every job would run with the *panel's* privileges unless carefully re-dropped per job. The right
way, and the one every real hosting panel actually uses, is real per-account crontabs: `crontab -u
<username>` installs the account's jobs into cron's own per-user spool, and cron itself runs them as
that exact user from then on — the same "the account's own uid does the work" boundary already
established for FTP uploads and disk quota, extended to scheduled tasks without inventing anything
new.

**The whole crontab gets regenerated on every write** — one `MAILTO=` line plus every enabled job,
written fresh each time rather than edited in place — the same pattern every other generated
artifact in this app already follows (nginx vhosts, DNS zones, vsftpd.conf). And validation didn't
need reinventing either: `crontab` already parses and rejects a malformed file, and — genuinely
useful, not just a side effect — it does this atomically. Feed it a bad file and the *previous*
crontab stays completely untouched; nothing else in this app got that revert-on-failure guarantee
for free, everywhere else it took an explicit backup-and-restore dance.

cPanel-style presets (Every Minute, Every 5 Minutes, Once Per Hour, and the rest) sit alongside
manual field entry, and each account gets its own Cron Email address — defaulting to their contact
email — so job output has somewhere real to go instead of piling up in a local mailbox nobody
reads.

Live-verified against a real disposable account on the actual dev server, not just the test suite:
added a job through the real form and confirmed it with `crontab -l` on the real Linux user;
deliberately fed the privileged action a broken crontab and watched it get rejected with crontab's
own actual error message, previous jobs still intact; removed the job, then removed the whole
account and confirmed the crontab went with it, cleanly, no orphan left behind.
