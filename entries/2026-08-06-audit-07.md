# Phase 68 - Security Audit #07, and the Escalation Path a Fix Almost Opened

Before the Software section's real item — a multi-app installer — the user asked for a full stop
and a full audit: everything shipped since #06, checked end to end, nothing moved on until it's
clean. That's ten sections' worth of work in one window: SSL/TLS, Databases, OS package
management, Packages & Resellers, Server Configuration, the Email section's ten items, Domains,
Files, the account-side Databases section, Metrics, DNS Lookup, Team Access — the largest single
authorization change of the whole project, a 44-controller pass — and real phpMyAdmin, built
earlier this same session. Split across six focused review passes plus a direct self-review of the
phpMyAdmin signon design, a full git-history secret scan, and live-server state verification.
Thirteen findings, all fixed the same day.

Two of them are worth dwelling on.

The first is the kind of bug this codebase has now hit three times: a real password, handed to a
privileged provisioning action as a plain command-line argument instead of through the established
root-owned-temp-file handoff. Two of the new database actions did it, and — worth checking rather
than assuming — so did two *older* actions that predate this window entirely, `db-user-create` and
`db-user-password`, which happened to share the identical pattern and had simply never been looked
at with this specific question in mind. `ps auxww` shows any process's full argument list to any
local user on the box for the process's whole lifetime, regardless of who owns it — confirmed
directly against `panel-dev`, whose `/proc` has no `hidepid` restriction, so this wasn't
theoretical. All three fixed the same way: root's own `mysql` needs no `-p` flag at all over its
unix-socket auth, so the SQL-statement actions just pipe the statement over stdin now; the one
action that authenticates as a real non-root user uses a `--defaults-extra-file` instead. The same
shape turned up a third time in phpMyAdmin's own signon token — a 60-second bearer credential,
found sitting on the same command line as a password that had correctly gone through the temp-file
path, right next to it. Same fix, same file.

The second is a smaller finding that came within one line of being a worse one. The account-level
DNS API had drifted from the big Team Access refactor entirely — still resolving accounts through
the pre-refactor `$request->user()->accounts()->firstOrFail()`, so a collaborator's API token could
never reach the account they actually collaborate on. Fixing just the resolver — swapping in
`Account::accessibleBy()`, the same call every web controller already uses — would have been a
one-line, obviously-correct-looking change. It would also have been wrong on its own: minting an
API token only requires the *`security`* Team Access permission, not `domains`, because API Tokens
sits under the Security nav group. A collaborator granted only `security` could already mint a
`dns:write` token; today it just doesn't work, because the resolver 404s first. Fix the resolver
alone and it would start working — for someone who was never granted DNS access at all. Both
halves went in together: the resolver fix, and an explicit `requirePermission(..., 'domains')`
check the web controller already had and this one never did. A token's own ability is a ceiling,
never a substitute for the underlying permission — worth remembering as its own rule, since
nothing else in this codebase currently has two independent authorization layers stacked quite
like this one does.

Also closed: a Reseller's account-import run had no ownership check on its own detail page (the
other two actions on the same controller had it; this one didn't); a suspended reseller's
already-open session kept working indefinitely, since the suspension check only ever ran at
login; a nested archive inside account-import extraction had no independent safety check of its
own, relying entirely on GNU tar's incidental defaults; the challenge-response spam gate matched
an approved sender against the whole raw `From:` header instead of the parsed address, so
`"boss@example.com" <attacker@evil.com>` sailed straight through; DNS Lookup had no backend
permission check behind its UI gate, and its hostname regex allowed a leading dash into `dig`'s
own argument parsing; a user who both owns an account and collaborates on another had no
guaranteed resolution order between the two; admin webhooks could be pointed at loopback or cloud
metadata addresses; and phpMyAdmin's own signon session had no bound tying its lifetime to a
Team Access revocation, so a 24-minute stock PHP default was quietly the real answer to "how long
does access last after you remove someone" — now an explicit 15 minutes, actually enforced rather
than left to a 1%-per-request garbage-collection sweep.
