# Phase 80 - The Real Thing, Not a Reimplementation

The largest item still open on the gap list: Statistics Software Configuration. The existing
Traffic & Visitors page already parses nginx access logs directly for requests, unique visitors,
response codes, and top pages — but real AWStats does something genuinely different: browser, OS,
search-engine, and referrer breakdowns, built up as real month-over-month history. Worth building
as the actual tool, not another homegrown log parser wearing its name.

## Confirmed against the real thing before writing a line of the design

Everything about how AWStats actually works got confirmed against a real install on the dev server
before any code went in: the apt package, the exact per-domain config format, and — the part that
mattered most — whether its own historical database survives this panel's log rotation. It does.
AWStats keeps its own persisted state (`DirData`) separate from the raw log file it reads, so as
long as an update runs at least once before a month's log gets rotated away, that month's data is
in AWStats' own database forever, independent of whether the raw log evidence still exists.

Static HTML only — no live Perl CGI ever exposed to a request, matching the same "no execution
surface for untrusted paths" posture phpMyAdmin and File Manager already hold to. The provisioning
script's `awstats-update` action writes a config, updates AWStats' internal state, then builds the
main report page plus all 18 detail sections as static files, closing out the previous month's own
snapshot the first time it runs after that month ends.

## Two real bugs, two real fixes, neither of them guessed

**php-fpm's own sandboxing.** This server already locks `/etc` down to an explicit allowlist per
feature (`ReadWritePaths=`) — a pattern this same file has hit and fixed a dozen times before for a
dozen other features. AWStats writing its own per-domain config to `/etc/awstats` was no
exception: a bare `Read-only file system` the first time Update Now was clicked for real, fixed by
adding the one new path.

**A relative-link trailing-slash trap.** The month-picker link on the new Metrics page pointed at
`/account/awstats/{site}/{month}` — no trailing filename. AWStats' own generated report links to
its icons via a relative `../icon/...` path, and a URL with no real trailing segment gets treated
by the browser as *itself* being a file one level up from where it looks — so the relative path
resolved one directory too high and dropped the site ID entirely. Every icon 404'd. Fixed by
linking the real filename explicitly, confirmed via the network tab that every icon request
actually landed where it should.

Both were caught by watching the real page in a real browser against real generated output, not by
reasoning about the code in the abstract — exactly why this discipline exists.
