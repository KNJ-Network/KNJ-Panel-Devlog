# Phase 101 - Deploy from Git Rebuild, and a Real Subdomains Feature to Build It On

The user's own words set the scope, verbatim: *"i want you to fully rebuild the deploy from git
part of our panel to work exactly like the one in aapanel especially with the key side of things
so it can pull from private repos etc and then once we have rebuilt that we can commit it and
deploy it and cut a new version then update the test server then test this for real on the test
server, until we do all this our web server move and dns plan is on hold."*

The web-server-move / DNS plan (a much bigger, separate piece of work — moving KNJ's own website
onto its own panel install, standing up KNJ's own authoritative DNS) stays exactly where it was:
on hold, until this shipped and was proven live.

## Comparing against the real thing first

Before writing any code, the actual gap got checked against aaPanel's real "Create for Git" dialog
(inspected live, screenshot from the user) and aaPanel's own docs on how their auto-deploy
mechanism works. Three genuine functional gaps, not just polish:

1. **HTTPS-only, no private repos.** The existing feature hardcoded `GIT_ALLOW_PROTOCOL=https` and
   required an `https://` URL — no way to pull a private repository at all.
2. **No post-pull build step.** A pull was a raw `git fetch && reset --hard && clean -fd` — no way
   to run `composer install`, `npm run build`, or anything else after a deploy.
3. **Branch was free-text.** No way to see what branches actually exist on the remote before typing
   one in.

## A prerequisite nobody expected: KNJ Panel had no subdomains at all

The plan for the create form's domain picker assumed the App Installer's own domain-choice
mechanism could be reused. Checking the App Installer directly disproved that — it has no
domain/subdomain choice at all, hardcoded to the account's one primary site. Worse: an explicit
comment in `ParkedDomainsController` said outright that every non-primary `Site` row is an
addon/parked domain, "there's no separate subdomain concept." Confirmed against real cPanel
(trycpanel.net) that a genuine Subdomains feature is a real, distinct, cheap-to-support thing —
`blog.example.com` is a folder inside the parent's own `public_html`, one new DNS record in the
*existing* zone (no new zone), and its own separate Let's Encrypt cert. So Subdomains got built
first, as its own standalone feature, before Deploy from Git could depend on it.

## What shipped, in build order

1. **Real Subdomains** — `SubdomainService`, `parent_site_id` on `Site`, new
   `add-subdomain`/`remove-subdomain` provisioning script actions. Document root is
   `public_html/{label}` inside the parent account's existing tree; one new `A` record on the
   parent's existing DNS zone; SSL reuses the exact same `RetryIssueSslJob` every other site
   already goes through. Removal deliberately leaves the folder in place (matching cPanel's own
   behavior) and only tears down the vhost/cert.
2. **SSH deploy keys** — one reusable ed25519 keypair per hosting account (not per-repo, matching
   aaPanel's own model), generated by a new `git-deploy-ssh-keygen` provisioning action and stored
   `'encrypted'`-cast on `Account`. Never written to the account's own `~/.ssh` — the private key
   only ever gets written back out to a short-lived `/tmp` file, once, for the duration of a single
   clone/fetch/branch-listing call, then deleted — same discipline `CpanelTransferService` already
   used for its own remote-server SSH key.
3. **SSH-capable clone/fetch + branch listing** — `git-deploy-init`/`git-deploy-pull` now detect
   HTTPS vs SSH from the repo URL itself and branch accordingly (`GIT_ALLOW_PROTOCOL` set to match,
   never trusted from the URL string alone). Branch listing (`git ls-remote --heads`) runs directly
   from the app process, not through the privileged script — it's read-only and never touches an
   account's filesystem, so it doesn't need root.
4. **Custom post-deploy build scripts** — a new nullable `deploy_script` column on `git_repos`,
   delivered to the provisioning script the same temp-file-never-argv way as every other sensitive
   payload, run via `runuser -u "$USERNAME" -- bash "$SCRIPT_TMP"` with `cwd` set to the deploy
   path. The provisioning script has no `set -e`, so a naive implementation would have silently
   swallowed a failing build — fixed by explicitly `fail()`-ing the whole action on a non-zero exit,
   so a broken build now correctly fails the deploy run instead of reporting success.
5. **Rebuilt create form** — replaced the old free-pick "any existing site" dropdown with aaPanel's
   own two-choice shape, adapted for an account that already has a domain: deploy onto the main
   domain, or create-and-deploy-onto a brand new subdomain in the same step. Website Path preview
   updates live with the choice. Branch can be fetched from the real remote via a new JSON endpoint
   instead of typed blind.

## Two bugs found only by testing live, not by reading the code

The user's own standing instruction — test in Chrome, don't just trust a code read — caught both of
these, exactly as intended:

- **A failed clone left an orphaned subdomain behind.** The create form creates the subdomain
  first, then clones into it. Deliberately triggering a clone failure (wrong branch name) proved
  the subdomain wasn't rolled back — it stayed behind with nothing deployed inside it, and then
  blocked retrying under the same label with "already exists." Fixed: the controller now destroys
  the just-created subdomain if the clone that follows it fails.
- **Removing a subdomain leaves its folder on disk (by design, matching cPanel), which then blocks
  reusing the same label.** Not a bug — cPanel does the same thing — but worth writing down here
  since it surfaced mid-testing and cost a few minutes of confusion before the existing doc comment
  on `remove-subdomain` explained it.

## Live verification, end to end, on `panel-dev`

Per the user's own redirect mid-session — *"use the dev server as there is a real account on there
and it already has its dns working correctly... there is no harm testing the git deploy on the
actual dev server, whatever works on that will work on the test server and any other server too,
as that's what we actually cut from"* — the actual feature testing happened against `panel-dev`'s
real `test@knj.network` account (real DNS, real Let's Encrypt), in Chrome, not headless:

- SSH deploy key generated, real `ssh-ed25519 ...` public key displayed.
- Branch fetch against a real public GitHub repo (octocat/Hello-World) — correctly found all 3
  branches and defaulted to the real `master` branch.
- A real HTTPS clone onto the main domain, with a custom deploy script (`echo "build ran at
  $(date)" > BUILD_MARKER.txt`) — confirmed on disk afterward with the real timestamp, proving the
  script actually ran as the account's own user, not just that the panel claimed it did.
- A full main-domain → new-subdomain deploy round trip: subdomain created, DNS resolving
  (`dig @127.0.0.1`), a genuine per-host Let's Encrypt certificate issued (`openssl s_client`
  showing `CN = octoproj.test.knj.network`, not the box's own cert), files landing in the correct
  nested path (`public_html/octoproj/app`).
- The orphaned-subdomain bug above, found, fixed, and re-verified — the exact same subdomain label
  correctly succeeded on retry once the fix shipped.

## Shipped and tested for real, per the original instruction

Full local suite green throughout (1509 tests by the end), `pint --test` clean on every commit.
Cut as v0.16.16, synced to `repo.knj.network`, and upgraded onto `knj-test-server` via its own
real "Update Now" button — not just `panel-dev`'s auto-deploy — closing the loop the user asked
for: cut a version, update the test server, prove the whole release/upgrade mechanism carries it
correctly. Migrations for both new columns (`ssh_deploy_private_key`/`ssh_deploy_public_key` on
`accounts`, `deploy_script` on `git_repos`) ran clean on that real upgrade.

One deliberate gap, left open rather than silently skipped: a live SSH clone of an actual *private*
repository was not tested end-to-end this session — doing so would mean adding this account's
deploy key to a real GitHub repo's settings, which reaches outside the panel itself. The SSH code
path is covered by unit tests (asserting the temp key file argument is actually passed to the
script) and mirrors `CpanelTransferService`'s already-proven SSH pattern closely, but a genuine
private-repo test is worth doing before calling this fully closed.

With this shipped, deployed, and live-verified, the web-server-move / DNS plan is no longer
blocked — it resumes as its own separate piece of work.
