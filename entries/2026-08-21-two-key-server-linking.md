# Phase 102 - Two-Key Server Linking, Replacing the Shared Token

## A document_root bug sweep first

Before this, a quieter fix: several features that write to an account's document root — the
cPanel importer, custom Error Pages, Directory Privacy, the File Manager, and WebDAV account
setup — carried a stale assumption about where that root actually was. Deploy from Git and the
App Installer had already taught the panel that an account's real serving root can move (a git
deployment, a subdirectory install), but these five hadn't caught up. Root-caused and fixed
together, with regression tests covering all five, rather than patched one at a time as each was
individually reported.

## Replacing the shared linking token

DNS-only server linking has worked since Phase 99 on a single shared `agent_token` — one secret,
generated on Main, that authenticated traffic in both directions. Revisiting it surfaced a real
design question: a single bidirectional secret is weaker than it needs to be, and the exchange
itself required a live HTTP call from the satellite back to Main during linking, which meant
linking could fail on nothing more than a firewall rule.

The replacement is a two-key mutual-auth scheme, entirely offline:

- **Link Key** — generated on Main, always the first step (Manage Servers → Add Server → pick a
  role). Encodes Main's own hostname, IP, port, and a freshly-minted secret.
- **Response Key** — generated by the satellite when the Link Key is pasted into its own setup
  screen. Encodes the satellite's own hostname/IP/port, its own freshly-minted secret, and an
  HMAC over that payload keyed on the Link Key's secret — cryptographic proof it genuinely held
  the real key, not a guess.
- Pasting the Response Key back into Main's **Complete Link** box verifies that HMAC and finishes
  the link.

Two independent secrets — one per direction — replace the one shared token, and the whole
handshake never touches the network. The only live authenticated call left is the *existing*
zone-membership sync (`PushZoneMembershipJob`), which now also carries the TSIG key delivery that
used to happen once, at link time.

## Two bugs the live test caught

Local tests passed clean before any of this touched real infrastructure. The live test — upgrading
the actual test DNS-only box (`knj-dnstest-server`, already linked under the old scheme, via its
own real "Update Now" — not a shortcut) — caught two things the test suite couldn't have, because
neither is visible from a fresh database:

1. **Adding a server with DNS clustering already enabled crashed.** A freshly-added satellite has
   no IP yet — that only arrives once linking completes — but the cluster-config builder
   interpolated it straight into BIND's `also-notify` directive anyway, producing a malformed
   config line that failed BIND's own validation. Fixed by leaving unlinked servers out of the
   notify list (the key-authentication part doesn't need an IP at all) and re-registering the
   server once linking actually supplies one.
2. **A box already linked under the old scheme couldn't get back to the linking screen.** The
   migration that removed the old `agent_token` column left hostname and IP address alone — they
   survive intact. But the code deciding whether to show "already linked" vs. "here's where to
   paste a key" was keying off *those* fields, not off whether a real secret existed. A server in
   exactly that in-between state — real address, no working secret — looked fully linked and hid
   the only way back to completing one, on both sides of the link.

Both were only reachable by actually running the upgrade against a real, previously-linked
install — which is exactly why the plan was to prove this against `knj-dnstest-server` before
calling it done, rather than trusting a green test suite against a database that had never seen
the old scheme in the first place.

## Verified end to end, for real

With both fixes shipped, the full loop was re-run against the real box: a Link Key generated on
Main, decoded by the satellite via its real setup screen, a Response Key generated back, HMAC
verified on Main, the link marked `Pending`, and then a real authenticated sync — triggered
on demand rather than waiting for the 15-minute sweep — flipped the server to `Online` and
delivered a fresh TSIG key, confirmed by reading it straight out of the satellite's own database
afterward. Three releases went out over the course of this (v0.16.19 for the linking system
itself, v0.16.20 and v0.16.21 for the two fixes the live test surfaced), each one actually
installed on the real test box before moving to the next step.
