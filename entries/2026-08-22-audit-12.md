# Phase 113 - Audit #12: The Setup Wizard's Missing Invariant

112 commits since Audit #11 five days ago — the largest window this project has covered, spanning the
DNS-only role's remaining buildout, the first-run setup wizard, the two-key mutual-auth server linking
system, and the full Mail Only epic (Stages 1 through 4, plus this week's closeout pass). Reviewed as
five parallel, dimension-focused passes rather than one linear read, since the diff genuinely spans
distinct attack surfaces: the privileged provisioning script, the new cross-server linking/dispatch
subsystem, cross-account authorization, a git secret scan, and — since it's an entirely new
pre-authentication surface — a dedicated pass on the setup wizard.

## The real bug

Three of five review passes came back clean: the provisioning script diff, the cross-account
authorization sweep, and the git secret scan. The other two — cross-server linking and the setup
wizard — converged on the same root cause reached two different ways.

The setup wizard's `admin()`/`storeAdmin()` steps check `session('setup.terms_accepted')` before
running. Every step after that — `basics()`, `storeBasics()`, `linkDns()`, `storeLinkDns()` — had no
check at all. `finish()` unconditionally sets `setup.completed_at`, which permanently 404s every setup
route except the congratulations page and stops `knjpanel:generate-setup-token` from ever minting a
replacement. Public registration is disabled, so the wizard is the *only* supported way to create the
first admin account. Reach any of those later steps out of order — a direct POST, a link crawler,
browser prefetch, anything holding just the setup token — and the install is permanently locked out of
ever having an admin, no recovery short of a manual database edit.

The cross-server-linking pass found the sharper edge of the same gap independently: with no admin
check gating `storeLinkDns()`, an attacker holding only the setup token could submit a self-forged Link
Key with an attacker-chosen secret, causing the satellite to register a "Main" server row with
`remote_secret_hash = hash(attacker's own secret)` — then authenticate as Main against that satellite's
own dispatch/sync endpoints indefinitely, no admin account ever needed.

One fix closes both: a real invariant check — does an admin account actually exist, not a session flag
that doesn't prove it — added to every step past admin creation, plus a final belt-and-braces check
inside `finish()` itself, since that's the one place that actually flips the permanent flag.

## What else turned up

- **Admin-creation race** — `storeAdmin()`'s exists-then-create check had no lock; wrapped in
  `Cache::lock()` so two concurrent submits can't both slip through and create two admins.
- **SSO signing key reused a comparison-only value.** `ServerSsoService`'s HMAC key was
  `hash('sha256', local_secret)` — bit-identical to the satellite's own `remote_secret_hash`, which
  every other consumer (`MailDispatchController`, `DnsOnlyZoneSyncController`) uses purely as a
  `hash_equals()` bearer-token comparison target. Reusing one value as both a signing key and a
  comparison target is a known anti-pattern — real-world impact was already narrow, but the fix was
  cheap: a domain-separation label run through `hash_hmac()` on both the mint and redeem sides.
- **No expiry on the setup token.** Added a 7-day lifetime, backward-compatible for any install whose
  token predates the fix. Caught a real bug testing this exact change: Carbon 3 changed `diffInDays()`
  to return a signed value by default (negative for a past date), so the first version of this check
  silently never triggered — `-8 > 7` is false. The test suite caught it, not a re-read of the code.
- **Defense-in-depth**: the two WordPress update actions were missing the `assert_path_within_home()`
  guard every sibling App Installer action has. Traced and confirmed not currently exploitable — these
  run as the account's own user, and `document_root` can't contain `..` today — but added the guard
  anyway for consistency, in case that validation ever loosens elsewhere without a matching review here.

## Still open

`ServerController::completeLink()` trusts a decoded Response Key's hostname/IP without validation
before persisting it as a future dispatch destination, and `ProvisioningScriptRunner`'s
TLS-verification-bypass fallback inherits that same unverified value. This is the DNS-only linking
flow's original design, unchanged since before this audit's window — but the stakes changed: that
channel used to carry only a TSIG key, and now carries real mailbox passwords and private keys too.
Needs a dedicated design pass (a confirm-before-save UI step, and/or dropping the TLS-bypass fallback
in favor of a loud failure) rather than a rushed fix — carried forward, same discipline Audit #11 used
for its own genuinely open design questions.

## Verified

Full local suite (1,683 tests, up from 1,678 going in) and `pint --test` green after every fix. No live
server changes this pass — everything caught and fixed locally before reaching `panel-dev` or a linked
satellite; the next deploy cycle carries these out.
