# Phase 114 - Audit #13: DNS Only, Reviewed as a Role Not a Diff

Every audit in this series so far has scoped itself to "everything changed since the last one." This
one deliberately doesn't — the plan for today calls for a security audit of each of the three shapes
this panel ships in (Main, DNS Only, Mail Only) on its own terms, not folded into the next diff-shaped
pass. So this is Audit #13, DNS Only specifically, reviewed end to end regardless of when each piece
of it landed: role gating, the zone-membership sync channel in both directions, the linking/trust flow,
and the DNS Only actions in the provisioning script. Four parallel, dimension-focused passes, each
independently re-verified against the actual code before trusting anything a first pass turned up —
same discipline every audit here has used since #06.

## The real bug

Audit #12, two days ago, flagged something and deliberately didn't fix it: `ServerController::
completeLink()` trusts a decoded Response Key's hostname/IP without validating it before saving it as
where future traffic goes. That audit called it lower-stakes for DNS Only than for Mail Only, reasoning
that the DNS Only channel only ever carries a TSIG key.

This pass found the sharper edge sitting downstream of that same gap. `PushZoneMembershipJob` has a
fallback path for a satellite that isn't reachable over its configured hostname yet — falls back to
raw IP with certificate verification switched off, accepted at the time as reasonable since the IP
itself came from an authenticated admin, not attacker input. What that fallback path didn't account
for: when the push succeeds, the job reads a `hostname` field back out of the response and — with no
check on which connection it arrived over — writes it straight into the `Server` row. A one-time
on-path interception during that fallback window doesn't just expose the TSIG key in transit. It can
plant a hostname that redirects every future sync indefinitely, long after the interception itself
ends — and that same hostname is what the admin cross-server SSO feature redirects to when someone
clicks "log in" for that satellite. One MITM during a bootstrap window becomes a standing foothold that
outlives it.

The fix doesn't touch the underlying design question Audit #12 already flagged as needing real
thought — it closes the specific escalation on top of it: a self-reported hostname is only trusted when
it arrives over the TLS-verified connection, never the certificate-bypassed one. The self-correction
feature itself (a box linked before it had a proper hostname picks one up automatically) still works
exactly the same for the common case — a box that's actually reachable over its real hostname.

Also worth recording: re-examining that "TSIG key only" framing for DNS Only turned out not to fully
hold. The same push carries Main's own linking secret in the URL, and DNS Only boxes are a valid
target for the admin SSO flow with no extra restriction. Doesn't change what's tracked as open, but the
next person to do that design pass should know the DNS Only side isn't as low-stakes as it read two
days ago.

## What else turned up

Three smaller items, all defense-in-depth rather than live gaps:

- **The account (cPanel-equivalent) area had no explicit role check.** Not reachable today — no
  `Account` row can exist on a DNS Only or Mail Only box, and the account port is never opened for
  those roles — but this project has already learned once that one layer of enforcement isn't enough.
  Added the same explicit check every other role-sensitive area already carries.
- **One secret comparison used a database equality lookup instead of `hash_equals()`** — the sole
  exception to Audit #12's "every comparison is timing-safe" claim. Not a real timing channel against
  an already-hashed value, but brought in line with the rest of the codebase anyway.
- **A TSIG secret gets written unescaped into BIND config syntax**, safe today only because its one
  source (`tsig-keygen`'s own output) can't contain the characters that would matter. Added a charset
  check at the point it's first stored, matching the same "cheap insurance against provenance
  changing" reasoning Audit #12 used for a WordPress guard.

## Clean

Role gating, the zone-sync content path (every domain-creation entry point on Main enforces the same
strict hostname regex before a zone can exist), the linking/trust primitives (re-traced, not just
re-read from the changelog — Audit #12's admin-existence fix is present at all five relevant setup
steps), and every DNS Only action in the provisioning script against this series' established bug
classes. One pre-existing hardening gap noted for later — three provisioning actions write live BIND
config before validating it, unlike the zone-content path's safer temp-validate-then-move pattern — but
not fixed this pass, since every input reaching those actions is already validated upstream and a safe
fix needs a proper design for validating config fragments, not a rushed one.

## Verified

Full local suite (1,688 tests, up from 1,683 going in) and `pint --test` green after every fix.
