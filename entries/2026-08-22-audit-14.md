# Phase 115 - Audit #14: A Secret Worth More Than It Should Have Been

Second role-scoped audit in a row, same reasoning as yesterday's DNS Only pass: review the whole Mail
Only satellite role on its own terms rather than folding it into the next diff. Five parallel,
dimension-focused passes — role gating, the mail-dispatch channel, every Mail Only action in the
privileged install script, cross-account authorization across every mail-touching controller, and
cross-server admin SSO plus webmail session isolation.

## The real bug

Main talks to a linked Mail Only satellite through one endpoint: `/internal/mail-dispatch/{token}`. The
authentication on that endpoint was always sound — a timing-safe check against the linked server's
stored secret hash, the same pattern the DNS-only sync endpoint uses. What sat behind it wasn't: the
`action` parameter it accepts was validated only as "a string," then handed straight to the same
install script every role shares — one file, roughly 140 branches, no role check of its own inside it.
Every real caller in this codebase only ever sends mail-prefixed actions (create a mailbox, generate a
DKIM key, write a greylist config), so nothing was ever visibly wrong. But nothing stopped the endpoint
itself from accepting anything else the script knows how to do: stop a service, rewrite firewall rules,
reboot the box, touch a database. The route's own comments describe it as carrying "mailbox
create/delete, DKIM generation, etc." — in practice, holding that one secret was worth the box's root
account, not just its mail configuration.

Two independent review passes converged on this from different angles — one reading the dispatch
controller directly, the other reading the install script's dispatch block and noticing it had no
`PANEL_ROLE` gate anywhere in it. Fixed with an explicit allowlist: the exact 33 action names every real
caller in the codebase actually sends, cross-checked against every call site by hand. Anything else now
gets rejected before it ever reaches the script.

## What else turned up

- **The same DNS-only-only guard gap, mirrored.** `LicenceController`'s three actions checked only
  `ServerRole::DnsOnly`, even though both DNS Only and Mail Only are exempt from licence enforcement and
  neither has anything for a licence to actually do. A Mail Only box's admin could request a real trial
  licence a DNS Only box's admin already couldn't — the exact bug class that guard was written to close,
  just left open on the other satellite role. One shared exemption list now covers both.
- **Webmail's login form had no network-level brute-force protection.** Every other login in this app
  writes to a dedicated log channel a fail2ban jail watches; webmail's own `MailboxAuthException` handler
  never did. Not new to Mail Only — every role has this gap — but most consequential there, since Mail
  Only's other surfaces are deliberately locked down while webmail necessarily stays open (that's
  literally where the mailboxes live). Now logs to the same channel, same format, so the existing jail
  picks it up.
- **Two provisioning-script regexes let `..` through by omission.** The Dovecot auth-map "home" field
  and the mailbox-map "path" field both validated against a charset that happened to allow an all-dot
  value, so `../../../root` would have technically passed. Traced end to end: not reachable today, since
  the one real caller only ever builds these fields from an already-validated domain and mailbox name
  that can't produce `..`. But this script exists specifically because it doesn't trust its caller alone
  — so both got tightened to the same "no dots in the charset, rules out `..` by construction" shape
  already used everywhere else in the file, verified against a real value and a traversal payload before
  landing.

## What's carried forward, not fixed

Most of the Mail Only config-write actions in the install script write their content to the live path
first and validate afterward, reverting from a backup on failure — the same pattern flagged as Low in
yesterday's audit, just turning out to be the norm here rather than the exception. Every real caller
sends complete, pre-validated content, so this isn't reachable by an attacker today; it only matters if
the script itself gets killed mid-write. Given how many actions share the pattern, this needs a
deliberate pass converting each to validate-first-then-atomic-move, not a rushed fix squeezed into
today's review.

## Clean

The most thorough dimension by far was cross-account authorization — every mailbox, filter, greylist,
challenge-response, mailing-list, catch-all, and webmail code path traced back to an explicit ownership
check before touching data. Nothing found. SSO's key-derivation fix from two audits ago is still present
and correct; its landing surface on a Mail Only box stays infrastructure-only, no mailbox content
reachable through it. Webmail's IMAP/SMTP backend routing re-verified sound — mail hosting is a genuine
all-or-nothing cutover, so a routing mismatch can produce a broken inbox but not someone else's inbox.

## Verified

Full local suite (1,693 tests, up from 1,688 going in) and `pint --test` green after every fix. Both
regex fixes hand-verified against a legitimate value and a traversal payload, since this script has no
automated test harness of its own.
