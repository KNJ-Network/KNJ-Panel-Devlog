# Phase 137 - The Half of a Server Switch Nobody Had Built

Linking a Mail Only server and flipping the active mail server has always resynced every existing
mailbox's routing and auth maps immediately — `MailSettingsController::updateServer()` was already
solid on that front. What it never did, and never claimed to, was move the mail itself. A mailbox
created before the switch stayed exactly where it physically was; only the panel's idea of where to
route new traffic for it changed. Anyone actually depending on old mail being reachable after a
switch had no way to get it there short of an SSH session and a manual `rsync`.

Built the other half: a "Mailbox data migration" card on the Mail Settings page that runs a real,
queued, live-polled `MailMigrationRun` — pick a from/to server (Local or any linked Mail Only
satellite, either direction), hit Migrate, watch the log fill in as each mailbox gets processed.

The interesting design decision was the transport. The obvious shape — a dedicated upload endpoint
with a raised `client_max_body_size` for genuinely large Maildirs — ran straight into a bug this
project has now hit more than once: `issue-panel-cert` only regenerates an already-installed
server's live nginx vhost when an admin explicitly re-triggers "Set hostname." A new location block
added to that heredoc would never reach a server that was already running, without yet another
resync mechanism bolted on somewhere. Rather than build a fourth one of those, the whole feature
reroutes around the problem: each mailbox's Maildir is tarred and split into ~700 KB base64 chunks,
and every chunk rides the existing `/internal/mail-dispatch/{token}` channel every other mail action
already uses — the one that was already safely under nginx's stock 1 MB body-size default, on every
server, with zero new config to keep in sync anywhere.

That meant `ProvisioningScriptRunner::run()` needed a new sibling, `runAgainst($target, ...)`, since
a migration has to address the "from" and "to" server independently of whichever one
`mail.active_server_id` happens to point at right now — `run()` only ever knew how to ask "where's
mail active," never "talk to this specific server regardless."

Found one genuinely subtle test bug chasing this down, worth a note for next time: a strict
`failed_count === 0` check on a freshly `create()`d model was comparing against `null`, not `0`,
because Eloquent never reads a migration column's DB default back into the in-memory model unless
it was explicitly passed to `create()` — same class of gotcha the DNS Only cert-timeout fix hit two
weeks ago with `started_at`. And once that was fixed, one test still failed for an unrelated reason:
PHP arrow functions (`fn() => ...`) capture outer variables by value at definition time, not by
reference, so a mock closure referencing a transfer ID generated by an *earlier* mock call silently
compared against `null` forever. Regular closures with an explicit `use (&$transferId)` fixed it.

Full local suite (2471 tests) and `pint --test` both green. Deployed to `panel.dev.knj.network` and
confirmed live — the page renders, the form validates, the migration-run polling terminal works.
What it did *not* get was a real end-to-end chunked transfer against an actual linked Mail Only
satellite: `knj-mail-test-server`, this project's long-running Mail Only dev box, was decommissioned
the same day in preparation for the real production mail server build-out, so there was nothing left
to link against. That real proof — a genuine Maildir crossing two real boxes — comes from the
production Mail Only install once it exists, which is exactly the scenario this feature was built to
unblock in the first place.
