# Phase 221 - The Table That Only Ever Said One Thing

A table is a promise about the data underneath it: there's more than one dimension here,
worth a row and a column each. Every domain-picker built earlier this same day kept that
promise honestly — one column for a name, one for a link, nothing pretending to be richer
than it was. Correct, and also, once you actually looked at it sitting at the top of a dozen
different pages, heavier than the one thing it was ever actually saying: pick one of these.

## What a table costs when it only has one real column

A table announces rows and columns before you've read either. It reserves a whole card, a
header bar, a border, visual weight proportional to how much structure it's promising to hold
— and then, on page after page, delivers exactly one fact per row: a name. The single
"Manage" link in the second column wasn't information, it was the same action repeated once
per row, dressed as if it varied. Twelve pages had independently arrived at the identical
shape for the identical reason, which is usually the sign that the shape itself, not any one
instance of it, was asking for revision.

## Consolidating without assuming uniformity

The instinct once you notice twelve nearly-identical blocks is to collapse them into one
version and stop there. That instinct is right about eleven of them and wrong about the
twelfth, which is exactly why it's worth checking each one instead of trusting the pattern
match. One of the twelve wasn't carrying a bare name at all — its own version of this table
had a status badge, an issuer, an expiry date sitting in the row next to the domain, real
information a plain dropdown has no room for. Folding it into the same simplification anyway
would have quietly deleted data nobody asked to lose, in the name of a consistency that
wasn't actually free. Noticing the exception mattered more than executing the rule.

## The one page that needed a different shape entirely

A second page didn't need a lighter version of the same control — it needed a different
control. Everywhere else, "pick a domain" meant narrowing what you're looking at down to one
thing. On this one page, the most useful view was never a single domain at all; it was
everything, from every domain, side by side, with a domain-scoped view as the exception
rather than the rule. A dropdown can't express "and also show me the combined view" — it can
only ever point at one option at a time. That's not a case for a fancier dropdown. It's a case
for tabs, where "all of it" is a real, first-class choice sitting right next to the specific
ones, not something bolted on after the fact.

## What stayed the same on purpose

Nothing about how a choice actually gets submitted changed underneath either version. The
part that decides which domain a new record belongs to, the part that checks you're allowed to
touch the one you picked — none of that moved. Only the part a person actually looks at did.
The right amount of change here was exactly the surface, not an inch more.
